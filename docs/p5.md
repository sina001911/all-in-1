# P5 — Specialist Layer, HITL Workflow Orchestration, Observability

P5 is the first implementation of the specialist layer P1 declared but never
wired, plus the human-in-the-loop orchestration the safety guard described but
nothing ever called, plus the observability seam the execution path lacked.

**One sentence:** P5 turns a `SpecialistRequest` into a validated
`SpecialistResponse` by routing a role onto a capability through the P3 bridge
and executing it through the P4 engine — and only through that engine — then
orchestrates several such steps inside a bounded, human-gated loop, logging every
step with secrets redacted.

## What P5 does not do

P5 adds capability by *refusing* to add capability:

- **No file writes.** The workflow loop imports no filesystem API (pinned by a
  structural test). The only file writers are the OpenCode tools bound in P6.
- **No tools.** A specialist analyses; it never carries a tool surface. The
  `SpecialistRequest` type has no `tools` field by construction, and the runner
  enforces the same guarantee at runtime (`TOOLS_FORBIDDEN`).
- **No media.** No specialist is registered for generation or media-QA roles;
  they resolve to `SPECIALIST_NOT_FOUND`.
- **No new providers.** Only the deterministic local adapter and the two local
  models are registered. Opening a real provider still takes three explicit
  human acts (P4).
- **No dependencies.** Runtime dependencies remain zero. The schema validator is
  hand-written for exactly this reason.

## The specialist contract

```
SpecialistRequest  { role, prompt, inputs, outputSchema }
        │
        ▼  refuse if a `tools` field is present (runtime NoToolField check)
SpecialistRunner
        │  capabilityForRole(role)          ← P3 bridge, no bypass
        ▼
ExecutionEngine.invoke(selection)           ← P4 gates, unchanged order
        │  SELECT → VALIDATE → EGRESS → APPROVAL → RESERVE → INVOKE → SETTLE
        ▼
validateStructured(result.structured, outputSchema)
        │
        ▼
SpecialistResponse  { ok: true, structured } | { ok: false, error }
```

The runner surfaces every engine failure as an `ok: false` response carrying the
typed code, so callers route a budget refusal, an egress refusal, and a provider
timeout the same way. It never throws for an expected failure; it throws only for
a caller bug such as an unusable schema (`SCHEMA_INVALID`).

### Schema validation

A deliberately minimal JSON-schema subset — `type`, `required`, `properties`,
`additionalProperties: false`, `items` — enough to pin a contract without a
validation library. Anything richer is *ignored*, not fatal, so a fuller schema
degrades to a looser check instead of rejecting a valid response. With no
`outputSchema` the structured output passes through unvalidated (and the
response says so, rather than implying a contract was met).

## Workflow orchestration and the human in the loop

P5 wires the frozen `safety/guard.ts` rules — `assertCanAnalyze`,
`assertCanPlan`, `assertAutoBounds`, `mustPauseForHuman` — which P1 declared and
nothing called.

| Mode | Analyze | Plan | Iterate |
| --- | --- | --- | --- |
| `INSPECT` | yes | **no** (`MODE_VIOLATION`) | no — pauses per step |
| `SUGGEST` | yes | yes | no — pauses per step |
| `BUILD` | yes | yes | yes, only with explicit `--auto` |

Semantics:

- Without `--auto`, the loop runs **exactly one step and pauses**
  (`pausedForHuman: true`, `ok: true`). Calling `run()` again continues from the
  next step. A human turn is required between steps.
- `--auto` is an explicit per-run opt-in. It is bounded by the frozen guard's
  hard limits, and the loop additionally clamps `maxIterations` to **5** even if
  a caller asks for more.
- `assertCanEdit` is intentionally **not** asserted: P5 has no edit action, so
  asserting it would wrongly refuse INSPECT and SUGGEST. The assertion belongs at
  the point a write is requested, which is the P6 tool binding.
- The frozen guard's `dryRunFirst` requirement is **vacuously satisfied** in P5:
  it triggers only when `edits > 0`, and P5 never edits. This is stated rather
  than assumed, and is exactly why the guard's own defaults are preserved instead
  of relaxed.
- A **retryable** step failure escalates: the loop stops with
  `WORKFLOW_ESCALATED` and `escalated: true` even under `--auto`. A
  non-retryable failure stops and surfaces the step's error code.
- Cancellation is honoured between steps (`WORKFLOW_CANCELLED`), and a step's
  `signal`/`timeoutMs` are forwarded to the engine.

## Settlement guarantee

A reservation is taken before a call and settled on **every** exit path. P5 adds
the two exit paths P4 did not have: timeout and cancellation. The engine races
the adapter invocation against `timeoutMs` and the abort `signal`; on either, it
releases the reservation immediately and throws a typed `PROVIDER_TIMEOUT` /
`PROVIDER_CANCELLED` before the error propagates. The underlying promise is not
cancelled (that is the adapter's concern) — but the ledger cannot leak a
reservation because a caller abandoned the wait. Pinned in
`test/execution-settlement.test.ts` against an adapter that would otherwise block
forever.

The gate order is unchanged by the race: egress is checked before the race begins,
and the secret gate (inside the adapter) fires before any request is built. A
timed-out call to a non-allowlisted host still fails with `EGRESS_BLOCKED`, never
with a timeout.

## Observability and redaction

`LoggedExecutionEngine` wraps the engine (or any `InvocationPortal`) and emits
structured JSONL. It derives *which gate refused* from the typed error code —
`gate.refused.egress`, `gate.blocked.approval`, `gate.failed.invoke` — so the log
is a real audit trail without instrumenting engine internals. No gate behaviour
changes: the wrapper rethrows every error unchanged and returns every outcome
unchanged.

Redaction is defence-in-depth and both layers are tested independently:

1. The seam redacts provider-derived text (`result.text`, error messages) with
   `redact()` before logging, and truncates to 400 chars.
2. The logger redacts again — message and every string field — before any sink.

The raw provider payload (`result.raw`) is **never logged**, per the invoke-result
contract; a test plants a secret in `raw` to prove it never reaches a sink.

## CLI

```sh
# Structured analysis, offline and deterministic by default
node src/cli.ts specialist CODE_REVIEWER --text "function add(a,b)"

# Validate the output against an inline schema
node src/cli.ts specialist FAST_TASK --text "hi" \
  --schema '{"type":"object","properties":{"summary":{"type":"string"}},"required":["summary"]}'

# Vision from a captured artifact reference
node src/cli.ts specialist VISION --image shot-1

# Human-in-the-loop: pauses after one step in INSPECT
node src/cli.ts workflow INSPECT --steps CODE_REVIEWER,FAST_TASK --text "check this"

# SUGGEST produces a plan
node src/cli.ts workflow SUGGEST --steps CODE_REVIEWER --plan --text "check this"

# BUILD with explicit, bounded autonomy
node src/cli.ts workflow BUILD --steps FAST_TASK,FAST_TASK,FAST_TASK --auto true --text "x"
```

stdout is exactly one JSON document (the result); the JSONL log stream goes to
**stderr** so the surface stays scriptable.

## Honest limitations

1. The deterministic local adapter returns a fixed structured shape
   (`{ summary }`). A specialist with a richer schema validates against real
   output only when a real provider is registered — which is off by default.
2. Cancellation abandons the wait, not the underlying call; adapters that ignore
   an `AbortSignal` keep running. The ledger is settled regardless.
3. A workflow step has no edit action, so a `--plan` in SUGGEST is a plan
   *summary* derived from structured outputs, not a diff. P6 binds the tools that
   make plans executable.
4. The observability seam reports the gate that refused a call from the typed
   error code; it does not emit per-gate events for a call that succeeded.
